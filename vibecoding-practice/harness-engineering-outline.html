AI 工程的三个阶段：Prompt、Context、Harness，优化对象各不相同

2023–2024

Prompt Engineering

优化一次调用里的措辞、few-shot、结构化输出。问题是：每次对话独立，错误难以积累成系统改进。

2025

Context Engineering

优化进入 context window 的信息质量，例如 RAG、记忆、目录结构、工具结果。它提升单次任务成功率，但仍不解决“下次别再犯”。

2025–

Harness Engineering

优化 agent 长期工作的运行环境，包括规则、工具、约束、反馈环和 evals。重点从“这次答对”转向“系统越来越可靠”。

第一部分 · 什么是 Harness

Agent = Model + Harness，Harness 是模型之外让 agent 可靠运行的全部基础设施

Four Layers

一个最实用的拆分方式

如果把 Harness Engineering 放到 vibecoding 场景里看，核心不是“再写一个更长的 prompt”，而是把 agent 的工作环境拆成四层，分别解决信息不足、执行不稳、结果不可验证、系统持续漂移这四类问题。

  • Context：行动前给信息。包括规则文件、目录说明、模块边界、任务背景和按需加载的局部文档。它解决的是 agent 不知道系统长什么样、因此总在错误心智模型上行动的问题。
  • Tools：把动作做实。包括脚本、linter、截图、测试运行器、格式化工具和小型自动化。它解决的是 agent 虽然“知道该做什么”，但没有稳定执行面的情况。
  • Feedback Loops：行动后看结果。包括 checklist、测试、agent review、截图比对、部署验证和 evals。它解决的是 vibecoding 里最常见的假阳性: 代码改了，但没人知道它到底能不能工作。
  • Entropy Management：防止系统越做越乱。包括把 harness 放进 git、持续维护规则文件、把常见失败沉淀成脚本或检查项。它解决的是项目一开始很好用，后来 context 过时、规则失效、agent 质量越来越不稳定的问题。

第二部分 · Agent 为什么出错

失败模式 1：上下文不清楚。在 kick-off 和后续开发里，模型会以两种不同方式把系统带偏

Stage 1 · Kick-off

开场描述不清，做出来的 app 可能从一开始就不是你想要的东西

  • 如果产品目标、用户路径、技术边界描述不清，模型会很快补齐细节，但补齐出来的是它理解的产品，不是你真正想做的产品。
  • 0→1 阶段最怕的不是写得慢，而是方向一开始就偏了，后面越做越像在错误前提上加速。
  • 做法不是立刻进入实现，而是先用 plan mode 和模型反复讨论，让模型持续 challenge 想法、补缺口、暴露歧义。
  • 直到拿到可执行的上下文基座，也就是下面这 6 份文档，再进入大规模 vibecoding。
Stage 2 · Build / Debug

后续描述不清，模型就修不好 bug，也很难在已有架构上稳定加功能

  • 一旦进入新功能开发和 debug，问题就不再是“要做什么”，而是“现在这个系统到底是怎么工作的”。
  • 如果上下文过时、边界模糊、文档没有维护，模型就会修不准 bug，或者在已有架构上加出新的耦合和回归。
  • 如果任务涉及前端，新功能和 debug 最好都带上 截图；视觉现状、交互状态和 bug 表现只靠文字描述通常不够，模型更容易误解你真正想修的东西。
  • 所以这 6 份文档不是 kick-off 一次性产物，而是后续开发过程中必须持续更新和维护的工作资产。
  • 真正有效的 context 不是“写过”，而是每次关键改动后都还和当前系统保持一致。
0→1 Production Example · DozyTale

在 DozyTale 里，我们把 context 落成了一组持续维护的项目文档

PRDdocs/product-spec.md：定义产品目标、核心体验和完成标准，避免一开始就把 app 做偏。
APP FLOWdoc/guest-mode-spec.md、doc/floating-mini-player-spec.md：把关键页面、交互路径和用户流程写清楚。
TECH STACKCLAUDE.md：写明 Flutter + FastAPI + Vue Admin、部署方式、常用命令和关键耦合点。
GUIDELINESAGENTS.md、CLAUDE.md：给出开发流程、目录入口、发布日志和防回归规则。
STRUCTUREbugfix.md、docs/observability-plan.md：记录重点保护文件、已知风险和系统边界。
PLANdoc/differentiation-brainstorm.md、doc/differentiation-features-plan.md、docs/refactor-practice-report.md：把 brainstorm、功能推进和重构计划持续落盘。

这些文档在 kick-off 阶段用来把想法聊透，在后续新功能开发和 debug 阶段则用来维持上下文新鲜度，避免模型只凭聊天历史和局部代码做判断。

第二部分 · Agent 为什么出错

失败模式 2：缺乏验证手段。没有 Sensor，Agent 无法知道生成的代码到底能不能部署

Sensor

有效的 feedback loop，至少要同时覆盖两类反馈

Computational确定性、快速、可频繁运行。适合承载测试、类型检查、linter、自定义脚本这类每次改动后都能自动触发的检查。
Inferential语义判断，慢但更接近真实质量。适合承载截图检查、browser use、AI review、LLM as Judge 这类“代码对了但体验不一定对”的验证。
OpenAI Example

把 UI 和 observability 直接暴露给 Codex

  • 一条验证线是让 Codex 直接驱动 DevTools，执行 UI 路径、做前后截图、修复后反复回放，直到结果干净为止。
  • 另一条验证线是把日志、指标和 traces 直接开放给 Codex 查询，让它能基于运行时信号定位问题，而不是只靠 diff 猜。
0→1 Production Example · DozyTale

在 DozyTale 里，我们把 feedback loop 做成三层

  • 现象：只看代码 diff 或本地一两个函数返回值，无法判断一次 vibecoding 改动到底有没有真的把产品链路修好。
  • 原因：`DozyTale` 不是单点函数，而是前后端协同的 production 系统；如果 feedback loop 只停留在“代码看起来对”，很多问题会留到真实使用阶段才暴露。
  • 怎么做：第一层是 linter 验证，每一次对话后自动执行。第二层是 服务 call API 验证，可手动触发，也可在每次 commit 后按改动文件映射测试项，用 pytest + httpx 做回归或补新测试。第三层是 前端 browser use 验证，同样支持手动或增量触发；`Argus` 维护 .argus/catalog.md，把改动映射到用户路径，再执行 Playwright，并把截图和报告写回 .argus/reports。

第二部分 · Agent 为什么出错

失败模式 3：随着开发推进，代码库发生架构漂移，context 质量下降，agent 越来越容易出错

Drift Loop

代码越乱，agent 越难理解；agent 越难理解，越会继续制造混乱

  • 修了 A 又坏了 B。
  • 局部补丁越来越多，系统整体越来越不可读。
  • 下一次任务看到的是更差的 context。
Countermeasures

把防漂移做成日常系统，而不是事后大修

  • 规则文件和 evals 一起版本管理。
  • 把经常回归的问题变成锁定测试。
  • 持续清理熵，而不是等系统坏透了再重构。
OpenAI Example

用显式架构边界和后台清理来对抗漂移

  • OpenAI 先把依赖方向固定下来：从底层类型、配置、数据访问，到服务、运行时和 UI，只能单向依赖。
  • 认证、连接器、遥测和 feature flags 这类通用能力，不允许散落在各层里，而是统一从一个入口接入。
  • 这些规则再交给自定义 lint 和结构测试执行，例如结构化日志、schema / type 命名、文件大小限制和平台可靠性要求。
  • 原文给的两条黄金原则也很具体：优先复用共享 utility；不要用 “YOLO 式” 方法探测数据，尽量在边界校验，或直接依赖 typed SDK。
0→1 Production Example · DozyTale

在 DozyTale 里，我们用 `debug.md` 约束修复范围

  • 现象：0→1 阶段最容易出现的不是“一个 bug 修不掉”，而是修了问题 A，顺手又把问题 B 带回来，代码越改越散。
  • 原因：vibecoding 很容易为了快速修通当前问题，顺手改动周边逻辑；如果没有约束修复范围和回归保护，架构漂移会越来越快。
  • 怎么做：我们在项目里专门放了一个 debug.md，把调试工作限制成“先理解问题、按 spec 精准修复、每次修完都验证、不要顺手重构周边代码、不要改无关文件”。同时在 bugfix.md / 项目规则里维护重点保护文件和已修复约束，要求修改这些文件前先读历史修复意图，防止修了 A 又把旧问题带回来。

第三部分 · 人的角色

人的角色从“修补 agent 输出”转向“改进产生输出的系统”

Old Mode

看输出、挑错、手工修补

每次都在对付同类错误，系统本身并没有变得更好。

New Mode

把错误变成 rule、tool、check

下次再遇到同类问题时，不再依赖人工记忆，而依赖系统自动约束和自动验证。

What This Means

工程师在做更高杠杆的事

你不是少写代码，而是在写让未来很多次代码生成都更可靠的系统。

最有价值的动作，不是“把这次错改对”，而是“让系统以后少犯这类错”。

第三部分 · 人的角色

Agent 当前明确不擅长的几类工作，恰好也是 Harness Engineering 最需要人的部分

Still Hard For Agents
  • 真正的 0→1 创新方向判断。
  • 大型未知代码库的深度重构。
  • 没有明确正确答案的优先级和取舍。
  • Harness 本身的设计：该加什么规则、什么算通过。
Why Humans Stay Central
  • 因为这些问题需要定义目标，而不是只执行目标。
  • 需要判断哪些错误值得被系统化，哪些只是噪声。
  • 需要权衡延迟、成本、可靠性和工程复杂度。
  • 需要决定哪些技能自己保留，哪些交给 agent。

0→1 Production Example · DozyTale：

  • 现象：开发过程中真正卡住进度的，不是“模型能不能再多写一点代码”，而是一些没有标准答案的工程判断。
  • 原因：像“要不要拆短 SSE”“什么时候才该补下一段”“什么体验算通过”这类问题，本质上是延迟、成本、可靠性的取舍，不是模型自己能定义的目标。
  • 怎么做：由人先定义通过标准和系统边界，再让 agent 在这些约束内实现；人的杠杆不在多写一点代码，而在决定什么该被做成 harness。

收尾

Harness Engineering 的三个建议

01

先把“失败模式”写进系统

不要只修这一次的输出。把 agent 已经犯过的错误沉淀为 AGENTS.md、协议、脚本或检查项，让系统下次少犯同类错误。

02

优先补 Sensor，再继续改 Prompt

如果 agent 不能在几十秒到几分钟内知道自己有没有做对，那继续调 prompt 的收益通常很有限。先补验证路径，杠杆更高。

03

把 Harness 当长期资产维护

规则文件、脚本、验证路径和 evals 都应当进入版本管理，被持续演化。否则 harness 会和代码库一起漂移，很快失效。

模型会继续变强，但积累在 harness 里的工程判断力不会被替换。

不要只优化模型回答得好不好，而要优化模型在你的系统里是否能长期、稳定、可验证地工作。 当产品要把生成、执行、验证和持续迭代连成一个真实系统时，护城河不是 prompt，而是你如何设计让 agent 可靠工作的环境。
