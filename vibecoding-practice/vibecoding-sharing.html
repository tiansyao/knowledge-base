Vibe Coding 实战指南

不是 AI 有问题，是你没给 AI 可以依靠的东西。
系统比 Prompt 更重要。

四条核心原则

原则 01 → 章节二
文档是给 AI 的约束护栏
AI 在你的清晰度结束的地方开始幻觉。在写代码之前写文档， 不是为了存档，而是给 AI 划定边界：做什么、不做什么、 用什么技术栈、长什么样。文档即护栏，意图即代码质量。
原则 02 → 章节三
给 AI 可以验证自己的东西
提供测试用例、截图、预期输出。AI 有了验证手段， 就能自我迭代而不是等你来发现错误。 让 AI 知道"成功"长什么样，是比更好的 Prompt 更高杠杆的动作。
原则 03 → 章节四
上下文是最重要的资源
上下文窗口满了，AI 性能就降——遗忘早期指令、产生更多错误。 任务切换前 /clear，调查用 subagents，CLAUDE.md 保持精简。 无关的历史比没有上下文更糟糕。
原则 04 → 章节五
分工靠边界，防回归靠文档
多人或多 Agent 并行时，靠文件级分工和 Git Worktree 隔离，避免互相覆盖。 修完 bug 立即固化约束——跷跷板问题的根源不是 AI 能力， 是修复停留在对话里，没有落进 CLAUDE.md / lessons.md。

1系统 > Prompt

AI 的能力已经足够强——用一句话描述需求，它能写出可运行的代码。真正决定质量上限的，不是 Prompt 技巧，而是你给 AI 可以依靠的东西。

核心洞察

AI 是翻译器：把你的意图翻译成代码。意图越清晰、约束越完整，代码质量越高。AI 会话间没有记忆，每次新会话从零开始——没有系统，每次都在重建上下文。提升上限的路径不是更好的 Prompt，是更好的系统。

✗ Prompt 驱动
靠每次 Prompt 的质量
控制 AI 的行为

→ 好结果依赖运气
→ 每次新会话从零开始
→ 错误会反复出现
✓ 系统驱动
文档约束 + 验证手段
+ 上下文管理 + 固化经验

→ AI 有边界，行为可预期
→ 跨会话保持一致性
→ 每次纠正都变成资产

同一个需求，两种输入的差距

Prompt 驱动 vs 系统驱动 
# Prompt 驱动：全靠 AI 猜
"帮我做一个 App，让用户可以发帖，现代感，要好看"
"看看哪里有 bug 修一下"
"把登录做完"

# 系统驱动：AI 有依据可以执行
"读 @CLAUDE.md 和 @progress.txt，实现 @IMPLEMENTATION_PLAN.md 步骤 2.1，完成后运行测试。"
"用 subagent 调查 src/auth/，找到 token 刷新的竞态条件，修复后更新 lessons.md。"
"按 @APP_FLOW.md § 3 实现登录页，样式参考 @FRONTEND_GUIDELINES.md 的设计令牌。"

后面四个章节，就是这个系统的四个组成部分：文档约束、可验证的步骤、上下文管理、经验固化。

2文档优先系统

在写任何代码之前，先让 AI 把你的想法打穿，再用对话结果生成规范文档。文档不是给人看的记录，是给 AI 划定边界的约束护栏。

Step 1：先撕碎想法

在 Plan Mode 下发这条 Prompt，让 AI 把你的方案问到没有盲点为止。

Prompt — Interrogation 
在写任何代码之前，在 Planning 模式下无尽地审问我的想法。
不要假设任何问题，问问题直到没有假设剩下。

# AI 会追问：这给谁用？核心行动是什么？需要保存什么数据？
# 错误时发生什么？需要登录？需要数据库？手机上工作吗？
操作

在 Claude Code / Cursor 右上角切换到 Plan Mode，AI 只读不写，专注推演逻辑。审问完毕确认无漏洞后再切回 Normal Mode。

Step 2：一键生成六份规范文档

Prompt 
基于我们的审问，生成规范文档：
PRD.md、APP_FLOW.md、TECH_STACK.md、FRONTEND_GUIDELINES.md、
BACKEND_STRUCTURE.md、IMPLEMENTATION_PLAN.md。
具体且详尽，没有歧义。
文件作用核心价值

APP_FLOW.md每个页面和导航路径防止 AI 猜测用户如何移动
TECH_STACK.md所有依赖锁定到精确版本消除幻觉依赖和随机技术选择

IMPLEMENTATION_PLAN.md逐步构建序列步骤越细，AI 猜测越少

3让每一步可验证

给 AI 提供验证手段是你能做的最高杠杆动作。AI 有了验证方式就能自我迭代，而不是等你来发现错误。

给每个任务一个验证标准

✗ 没有验证
实现一个验证 email 的函数
✓ 有验证
实现 validateEmail 函数。
测试用例：
- user@example.com → true
- invalid → false
- user@.com → false
实现后运行测试。
✗ 模糊
"让它看起来更好"
✓ 可验证
[粘贴截图] 实现这个设计。
截图结果与原始设计对比，
列出差异并修复。

Plan Mode 四步流程

1
Plan Mode — 探索 只读不写。理解现有代码结构，不做任何修改。
2
Plan Mode — 规划 要求 AI 生成详细实施计划。按 Ctrl+G 在编辑器中直接修改计划内容。
3
Normal Mode — 实施 + 验证 切回 Normal Mode 按计划编码，同时要求 AI 写测试并运行。让 AI 自我确认结果。
4
提交 描述性 commit message，可直接让 AI 执行 git commit 和 gh pr create。
CLI — Plan Mode 四步对应操作 
# Step 1: 进入 Plan Mode（UI 切换 / Cursor 模式按钮）
读取 src/auth/，理解现有认证流程

# Step 2: 仍在 Plan Mode，要求生成计划
我想加 Google OAuth，生成实施计划
Ctrl+G                        # 在编辑器中直接修改计划

# Step 3: 切回 Normal Mode，执行计划
按计划执行 Step 1，完成后跑 flutter analyze

# Step 4: 让 AI 提交
提交这次改动，写描述性 commit message
何时跳过 Plan Mode

修单行、改拼写、加日志 → 直接执行。涉及多个文件、架构决策、或不熟悉的区域 → 先规划。

4主动管理上下文

官方文档核心结论

上下文窗口是最重要的资源。窗口满 → LLM 性能下降 → 遗忘早期指令、更多错误。单次调试会话可消耗数万 token。

上下文操作指令

Claude Code — 上下文管理 
# 清理
/clear                        # 完全重置上下文（任务切换时用）
/compact                      # 压缩历史，AI 保留关键决策和代码状态
/compact Focus on API changes  # 指定压缩时重点保留什么

# 中断与回退
Esc                           # 中断执行，上下文保留，可立即重定向
Esc Esc  或  /rewind         # 检查点菜单：恢复对话/代码/两者，或从某点压缩

# 跨会话恢复
claude --continue             # 继续最近一次会话，不用重新解释上下文
claude --resume               # 从历史列表中选择
/rename oauth-migration       # 给会话命名，便于后续 --resume 查找

对话管理：三个核心技巧

官方文档把这三件事列为最高频操作，值得单独记住。

① 改变方向

AI 跑偏了，立刻按 Esc 中断。上下文全部保留，重新描述正确方向继续。不要等它跑完再说——越晚越耗上下文。

② 检查点倒带

AI 把代码改坏了，Esc Esc 或 /rewind 打开检查点菜单，选择只还原代码、只还原对话，或两者都还原。不用 git stash。

③ 恢复对话

关闭终端后上下文不会丢。claude --continue 接上最近一次，claude --resume 从列表挑。关闭前先 /rename 命名方便找。

操作 — 改变方向 
# 情景：AI 开始写一个你不想要的实现
Esc                    # 立刻中断，文件未被修改，上下文保留

# 然后直接重新描述（不用重新解释背景）：
等一下，不要改 token.ts。
我想在 middleware 层做，不是在 service 层。
按这个方向重新规划。

# 如果同一方向纠正两次还是不对 → 上下文已被污染
/clear                 # 清空重来，用更精确的 Prompt 开始
操作 — 检查点倒带 
# 情景：AI 改坏了几个文件，你想回到刚才的状态
Esc Esc   （连按两次）
# 或
/rewind

# 菜单选项：
  Revert conversation only    # 只还原对话记录，代码不动
  Revert code only            # 只还原文件改动，对话不动
  Revert both                 # 代码 + 对话全部还原到该检查点
  Compact from here           # 从这个检查点压缩，清理冗余上下文

# Claude Code 每次工具调用前自动保存检查点，随时可回退
操作 — 恢复对话 
# 关闭前先命名，避免 --resume 时找不到
/rename oauth-migration       # 给当前会话起个有意义的名字

# 下次打开终端
claude --continue             # 直接接上最近一次会话，上下文完整恢复
claude --resume               # 弹出历史列表，按名字选择
claude --resume oauth-migration # 直接指定会话名恢复

# 恢复后不用重新解释背景，直接继续：
继续昨天的工作，完成 Google OAuth 的 callback handler。

Subagents：上下文隔离的最强工具

调查代码库时 AI 会读大量文件，全部堆在主对话里会很快耗尽上下文。Subagents 在独立上下文窗口中运行，以摘要返回结果。

prompt 
# 独立上下文调查，不污染主对话
使用 subagents 调查 src/auth/ 如何处理 token 刷新

# 实现后用子代理做 review（新鲜上下文，不偏向刚写的代码）
用 subagent 审查这段代码，找边界情况和竞态条件

保护上下文的 4 个习惯

🧹 任务间 /clear

不相关任务切换前重置。无关历史比没有上下文更糟。

🤖 调查用 Subagents

读大量文件时用子代理，探索结果以摘要返回。

✂️ CLAUDE.md 保持精简

臃肿规则 = AI 忽略规则。每行都问：删掉它会犯错吗？

🔄 两次纠正后重来

同一问题纠正两次，上下文已被污染。/clear 重新开始。

5在 Vibe Coding 中分工合作

Git Worktree：多人 / 多 Agent 并行互不干扰

多个人或多个 Claude Agent 同时开发时，最大的问题是互相覆盖改动。Git Worktree 让每条分支有独立的文件系统，共享同一个 repo。

terminal 
# 为两个人/Agent 各建一个隔离的 worktree
git worktree add ../feature-auth feature/auth
git worktree add ../feature-dashboard feature/dashboard
git worktree list

# 各自在独立目录中启动 Claude 会话
cd ../feature-auth && claude --continue
cd ../feature-dashboard && claude --continue

# 完成后删除 worktree
git worktree remove ../feature-auth
Claude Code — worktree 原生命令 
# Claude Code 内置支持，一键创建隔离会话
/worktree   # 创建新 worktree + 新会话，做完选 keep 或 remove

Writer / Reviewer 模式

同一批代码，用两个独立 Claude 会话：一个写，一个用全新上下文审查。写代码的会话偏向于相信自己刚写的东西，新鲜上下文的 reviewer 更容易找到盲点。

terminal — Writer / Reviewer 分离 
# 会话 A（Writer）：在功能分支上写代码
cd feature-auth && claude --continue

# 会话 B（Reviewer）：全新上下文，不受 A 的偏见影响
cd feature-auth && claude
用 subagent 完整审查 src/auth/，找：
1. 边界情况和竞态条件
2. 未处理的错误状态
3. 与 API 合约不一致的地方

分工边界原则

做法说明
文件级拆分明确谁负责哪些文件，写进任务描述
接口先于实现前后端并行时，先约定 API Schema，各自对着 Schema 开发
共享文件只追加对 CLAUDE.md、配置 jsonl 等共享文件，只追加不修改已有行
合并前 review diff两个 Agent 都改了同一层，合并前先 git diff 确认无隐性覆盖

Debug 期的跷跷板问题

修 Bug A → Bug B 出现 → 修 Bug B → Bug A 回来。根本原因是没有把修复的约束条件写进文档，导致 AI 下次新会话把它撤销了。

✗ 跷跷板循环
修复 Bug A
→ AI 改了 foo.py:42
→ 测试通过，关闭会话

新会话，修 Bug B
→ AI 读不到上次意图
→ foo.py:42 被改回去
→ Bug A 复活
✓ 修完立即固化
修复 Bug A 后更新 CLAUDE.md：

# 已修复约束（不要改动）
- foo.py:42 必须用 async/await，
  改回同步会导致会话超时
  登录失败（Bug #23）

三层文档防回归

1
CLAUDE.md — 约束层 每次修复 bug 后，把不能改动的原因写进去。AI 下次会话自动读到。
2
lessons.md — 经验层 格式：问题 → 根本原因 → 修复方式 → 不要这样做的原因。每次纠正后更新。
3
bugfix.md — 保护层 记录关键文件的修复意图。修改相关文件前先查这里，防止无意回归。
lessons.md — 示例格式 
## [2025-06] 登录后会话超时
问题: 登录成功但刷新后跳回登录页
根因: token 刷新用了同步调用，慢网络下 race condition
修复: auth.py:refreshToken 改为 async/await + 加锁
约束: 不要把 refreshToken 改回同步，无论看起来多简洁
Debug 期的上下文纪律

每个 bug 开一个独立会话，修完立即更新 lessons.md，然后 /clear 再开下一个。不要在一个会话里又修 bug 又加功能——上下文会被失败尝试塞满。
